01 · Definición¿Qué es la Ingeniería de Datos?

La Ingeniería de Datos (Data Engineering) es la práctica de diseñar y construir sistemas para la agregación, almacenamiento y análisis de datos a escala. Los Data Engineers permiten a las organizaciones obtener insights en tiempo real de grandes conjuntos de datos.

📊
Definición IBM:

"Data Engineering transforma cantidades masivas de datos en hallazgos estratégicos valiosos, empoderando a los stakeholders con datos confiables, convenientes y seguros."

Misión del Data Engineer

Construir la infraestructura de datos que permite a científicos de datos, analistas y líderes de negocio acceder a los datos que necesitan cuando los necesitan.

   ├─ APIs                         ▼                      │      (ML/AI)

   ├─ Logs                    │        │              ├─────▶ Analistas
   ├─ Archivos               │        │              │      (BI/Reports)
   └─ Streaming              │        │              │
                              ▼        ▼              └─────▶ Aplicaciones
                          STORAGE  TRANSFORM              (APIs/Apps)

¿Por Qué es Importante?

  • Volumen: Las empresas generan más datos que nunca (petabytes)
  • Velocidad: Necesidad de procesamiento en tiempo real
  • Variedad: Datos estructurados, semi-estructurados y no estructurados
  • Valor: Los datos son el nuevo petróleo, pero necesitan refinarse
🎯
Analogía:

Si los datos son el petróleo crudo, el Data Engineer es la refinería que lo transforma en combustible utilizable (insights, modelos ML, reportes).

Detalle de Cada Fase

📥 1. Ingesta de Datos

Definición: Movimiento de datos desde fuentes diversas hacia un ecosistema unificado.

  • Fuentes comunes: Bases de datos (MySQL, PostgreSQL, MongoDB), APIs REST/GraphQL, Archivos (S3, SFTP), Logs, IoT, SaaS (Salesforce, HubSpot)
  • Métodos: Pull (polling), Push (webhooks), CDC (Change Data Capture)
  • Consideraciones: Schema evolution, latencia, volumen, idempotencia

⚙️ 2. Transformación de Datos

Definición: Proceso de limpieza, normalización y preparación de datos para su uso final.

  • Limpieza: Manejo de nulos, duplicados, outliers
  • Normalización: Formatos de fecha, monedas, unidades
  • Enriquecimiento: Joins con datos maestros, geocoding
  • Agregación: Cálculo de métricas, KPIs, resúmenes

📤 3. Servicio de Datos

Definición: Entrega de datos procesados a consumidores finales.

  • Analytics: Data Warehouse para SQL/BI
  • ML/AI: Feature stores y datasets de entrenamiento
  • Aplicaciones: APIs, reverse ETL a sistemas operacionales
  • Real-time: Streaming a dashboards y alertas

04 · PipelinesData Pipelines: ETL vs ELT

Los Data Pipelines son flujos automatizados que mueven y transforman datos. Existen dos paradigmas principales: ETL y ELT.

ETL: Extract, Transform, Load

ETL (Tradicional)

┌──────────┐      ┌──────────────┐      ┌──────────┐
│ EXTRACT  │ ───► │  TRANSFORM  │ ───► │   LOAD   │
│  Fuentes │      │   Servidor   │      │ Destino  │
└──────────┘      │   de ETL     │      │  (DW)    │
                  └──────────────┘      └──────────┘

• Transformación ANTES de cargar al destino
• Datos ya limpios y estructurados llegan al DW
• Menor carga en el sistema de destino

✅ Cuándo Usar ETL

  • Data Warehouses tradicionales (on-premise)
  • Cuando el destino tiene capacidad de cómputo limitada
  • Transformaciones complejas que requieren herramientas especializadas
  • Cumplimiento estricto que requiere filtrar datos sensibles antes de cargar

ELT: Extract, Load, Transform

ELT (Moderno)

┌──────────┐      ┌──────────┐      ┌──────────────┐
│ EXTRACT  │ ───► │   LOAD   │ ───► │  TRANSFORM  │
│  Fuentes │      │ Raw Layer │      │ Dentro del  │
└──────────┘      │  (Lake)   │      │   destino   │
                  └──────────┘      └──────────────┘

• Datos crudos se cargan PRIMERO
• Transformación en el destino (usando su poder de cómputo)
• Flexibilidad para retransformar datos históricos

✅ Cuándo Usar ELT

  • Cloud Data Warehouses (Snowflake, BigQuery, Databricks)
  • Cuando el destino tiene gran capacidad de cómputo (escalable)
  • Necesidad de acceso a datos crudos para diferentes casos de uso
  • Transformaciones que evolucionan frecuentemente

Comparación ETL vs ELT

Aspecto ETL ELT
Cómputo Servidor ETL separado En el destino
Flexibilidad Menor (schema definido) Mayor (schema on read)
Datos crudos No disponibles Siempre disponibles
Escalabilidad Limitada por servidor Elástica en cloud
Herramientas Informatica, Talend, SSIS dbt, Spark, SQL nativo
🚀
Tendencia 2025-2026:

ELT domina en arquitecturas cloud modernas. La combinación de ingesta ligera + dbt para transformaciones es el stack más popular.

Tipos de Bases de Datos

📊 Bases de Datos Relacionales (RDBMS)

Datos organizados en tablas con relaciones definidas.

  • Ejemplos: PostgreSQL, MySQL, Oracle, SQL Server
  • Uso: OLTP (transacciones), datos maestros
  • Lenguaje: SQL

🔷 Bases de Datos NoSQL

Esquemas flexibles para datos no estructurados o semi-estructurados.

  • Documentos: MongoDB, CouchDB
  • Key-Value: Redis, DynamoDB
  • Columnar: Cassandra, HBase
  • Grafos: Neo4j, Neptune

☁️ Cloud Storage

Almacenamiento de objetos para datos a escala.

  • AWS: S3 (Simple Storage Service)
  • Azure: Blob Storage, ADLS Gen2
  • GCP: Cloud Storage
  • Formatos: Parquet, ORC, Avro, Delta, Iceberg

06 · Data WarehouseData Warehouse

🏢
Definición:

Un Data Warehouse es un repositorio centralizado que almacena datos estructurados, optimizado para consultas analíticas (OLAP) y reportes de Business Intelligence.

Características

  • Schema on Write: Datos estructurados al cargar
  • Orientado a Consultas: Optimizado para SELECT, no INSERT masivos
  • Histórico: Mantiene datos a lo largo del tiempo
  • Integrado: Unifica datos de múltiples fuentes
  • No Volátil: Los datos no cambian una vez cargados

07 · Data LakeData Lake

🌊
Definición:

Un Data Lake es un repositorio que almacena grandes cantidades de datos en su formato nativo (estructurado, semi-estructurado y no estructurado) para procesamiento posterior.

Características

  • Schema on Read: Estructura definida al consultar, no al cargar
  • Almacenamiento barato: Object storage (S3, ADLS, GCS)
  • Cualquier formato: JSON, CSV, Parquet, imágenes, logs
  • Big Data ready: Escala a petabytes
  • ML/AI friendly: Datos crudos para entrenamiento

Arquitectura de Zonas

DATA LAKE ZONES (Medallion Architecture)

🥉 BRONZE (Raw/Landing)
   │  Datos exactamente como llegan de las fuentes
   │  Sin transformaciones, máxima fidelidad
   │  Formato: JSON, CSV, raw
   ▼
🥈 SILVER (Cleaned/Conformed)
   │  Datos limpiados y validados
   │  Deduplicación, tipos corregidos
   │  Formato: Parquet/Delta optimizado
   ▼
🥇 GOLD (Curated/Business)
      Datos agregados y listos para consumo
      Modelado dimensional, métricas calculadas
      Formato: Tablas optimizadas para BI/ML

Data Lake vs Data Swamp

⚠️
Peligro: Data Swamp

Un Data Lake sin governance, catalogación y documentación se convierte en un "Data Swamp" (pantano de datos): datos inutilizables porque nadie sabe qué contienen ni cómo usarlos.

Cómo evitarlo:

  • Implementar catálogo de metadatos (AWS Glue, Dataplex)
  • Documentar linaje de datos
  • Definir políticas de retención y limpieza
  • Aplicar controles de calidad en cada zona

El Data Lakehouse combina lo mejor del Data Warehouse (ACID, SQL, performance) con la flexibilidad y economía del Data Lake (formatos abiertos, cualquier dato, ML-ready).

Tecnologías de Table Format

Los formatos de tabla abiertos habilitan capacidades de Data Warehouse sobre almacenamiento de Data Lake:

🔷 Delta Lake (Databricks)

  • ACID transactions sobre Parquet
  • Time Travel (versionamiento)
  • Schema evolution
  • Merge (upserts) eficiente

🧊 Apache Iceberg (Netflix)

  • Formato abierto y vendor-neutral
  • Hidden partitioning
  • Table evolution sin rewrite
  • Soporte multi-engine (Spark, Trino, Flink)

🪶 Apache Hudi (Uber)

  • Optimizado para streaming incremental
  • Record-level updates eficientes
  • Change Data Capture nativo
📈
Tendencia 2025-2026:

Apache Iceberg está ganando como el estándar de facto por ser el más agnóstico de vendor. Snowflake, BigQuery y Databricks ahora soportan Iceberg nativamente.

09 · ProcessingProcesamiento Batch vs Streaming

Procesamiento Batch

📦 Batch Processing

Procesa grandes volúmenes de datos en intervalos definidos.

  • Latencia: Minutos a horas
  • Casos de uso: Reportes diarios, entrenamientos ML, ETL nocturno
  • Herramientas: Apache Spark, Hadoop MapReduce, dbt
  • Ventajas: Más simple, más barato, tolerante a fallos

Procesamiento Streaming

🌊 Stream Processing

Procesa datos continuamente conforme llegan.

  • Latencia: Milisegundos a segundos
  • Casos de uso: Detección de fraude, monitoreo IoT, dashboards real-time
  • Herramientas: Apache Kafka, Apache Flink, Spark Streaming
  • Ventajas: Insights inmediatos, reacción rápida

Comparación

BATCH                          STREAMING

Datos ──► [Acumular] ──► Procesar   Datos ──► Procesar ──► Resultado
          (horas)        │                    (ms-seg)     inmediato
                         ▼
                    Resultado
                    (después)

Ejemplo:                          Ejemplo:
"Ventas totales de ayer"          "Alertar si venta > $10K ahora"

Arquitectura Lambda vs Kappa

λ Lambda Architecture

  • Combina batch + streaming en paralelo
  • Batch layer: Procesa datos históricos (completo, lento)
  • Speed layer: Procesa datos recientes (rápido, aproximado)
  • Serving layer: Combina ambas vistas
  • Desventaja: Duplicación de lógica en dos sistemas

κ Kappa Architecture

  • Solo streaming: Todo se procesa como stream
  • Reprocesar histórico reproduciendo eventos
  • Herramienta típica: Apache Kafka + Flink
  • Ventaja: Una sola codebase, arquitectura más simple

El lenguaje más importante para data engineering.

Para procesamiento distribuido de alto rendimiento.

Creciendo rápidamente en tooling de datos.

12 · OrchestrationOrquestación de Workflows

La orquestación coordina y programa la ejecución de pipelines de datos, manejando dependencias, reintentos y monitoreo.

Principales Orquestadores

🌬️ Apache Airflow

El estándar de la industria.

  • DAGs (Directed Acyclic Graphs) en Python
  • Enorme ecosistema de operadores
  • Managed: Astronomer, MWAA, Cloud Composer
  • Ideal para: Equipos establecidos, workflows complejos
from airflow import DAG
from airflow.operators.python import PythonOperator

@dag(schedule="@daily")
def my_pipeline():
    extract >> transform >> load

🗡️ Dagster

Moderno, asset-centric.

  • Enfoque en "Software-defined assets"
  • Type system robusto
  • Testing integrado
  • Ideal para: Equipos que quieren modern practices

🔮 Prefect

Pythonic y flexible.

  • Decorators simples (@flow, @task)
  • Hybrid execution model
  • UI moderna
  • Ideal para: Developers que prefieren simplicidad

🧙 Mage

Notebook-style, visual.

  • UI interactiva tipo notebook
  • Blocks reutilizables
  • Fácil para principiantes
  • Ideal para: Prototipado rápido, equipos pequeños

Conceptos de Orquestación

DAG (Directed Acyclic Graph)
              ┌──► Task B ──┐
Task A ──────┤              ├──► Task D
              └──► Task C ──┘

Conceptos clave:
• Schedule: Cuándo ejecutar (cron, eventos)
• Dependency: Qué tareas dependen de otras
• Retry: Reintentos en caso de fallo
• Backfill: Ejecutar para fechas pasadas
• SLA: Alertas si no completa a tiempo

13 · ObservabilityData Quality y Observabilidad

La observabilidad de datos permite detectar, diagnosticar y resolver problemas de calidad antes de que impacten al negocio.

Pilares de Data Observability

Los 5 Pilares (según Monte Carlo)

1. FRESHNESS  ─ ¿Los datos están actualizados?
2. VOLUME     ─ ¿Llegó la cantidad esperada de registros?
3. SCHEMA     ─ ¿Cambió la estructura de los datos?
4. DISTRIBUTION ─ ¿Los valores están en rangos normales?
5. LINEAGE    ─ ¿De dónde vienen y a dónde van los datos?

Herramientas de Data Quality

✅ Great Expectations

  • Open source, Python-based
  • "Expectations" como tests de datos
  • Documentación automática
  • Integra con Airflow, Spark, pandas
# Ejemplo de expectation
validator.expect_column_values_to_not_be_null("customer_id")
validator.expect_column_values_to_be_between("age", 18, 120)

🔷 dbt Tests

  • Tests integrados en transformaciones
  • Tests de schema: unique, not_null, accepted_values
  • Tests custom con SQL
# schema.yml
models:
  - name: customers
    columns:
      - name: customer_id
        tests:
          - unique
          - not_null

🔭 Monte Carlo

  • Data observability platform (commercial)
  • Detección automática de anomalías con ML
  • Linaje end-to-end
  • Alertas proactivas
⚠️
Data Downtime:

Según Monte Carlo, las organizaciones experimentan un promedio de 15 horas de data downtime por semana debido a problemas de calidad.

🏪 Feature Store

  • Splits reproducibles (train/val/test)

  • Real-time inference: Features on-demand

  • Monitorear cambios en distribución de datos
  • Alertar cuando el modelo puede degradarse
  • Herramientas: Evidently, WhyLabs, Arize
🎯
Regla del 80/20 en ML:

El 80% del esfuerzo en proyectos de ML es data engineering (obtener, limpiar, preparar datos). Solo el 20% es modelado.

15 · DataOpsDataOps y Mejores Prácticas

Definición:

DataOps es la aplicación de prácticas de DevOps a data engineering: automatización, CI/CD, testing, monitoreo y colaboración.

Prácticas de DataOps

🔄 1. Version Control para Datos

  • Código de pipelines en Git
  • Configuraciones y schemas versionados
  • Data versioning con DVC, LakeFS, Delta Time Travel

🧪 2. Testing

  • Unit tests: Funciones de transformación
  • Integration tests: Pipelines end-to-end
  • Data tests: Validaciones de calidad
  • Contract tests: Schema compatibility

🚀 3. CI/CD para Pipelines

  • PR reviews para cambios en pipelines
  • Tests automáticos en cada commit
  • Deployment automatizado a staging/prod
  • Herramientas: GitHub Actions, GitLab CI, dbt Cloud

📊 4. Monitoreo y Alertas

  • Dashboards de salud de pipelines
  • Alertas por fallos o anomalías
  • SLAs de freshness y calidad
  • Herramientas: Datadog, Monte Carlo, Elementary

Mejores Prácticas Generales

✓ Diseñar pipelines idempotentes (re-ejecutables sin efectos secundarios)
✓ Documentar todo (schemas, pipelines, decisiones)
✓ Implementar backfilling desde el inicio
✓ Usar formatos columnar (Parquet, ORC) para analytics
✓ Particionar datos por fecha/región para performance
✓ Separar compute de storage en cloud
✓ Implementar schema evolution desde el diseño
✓ Usar staging environments para probar cambios
✓ Automatizar todo lo que se pueda automatizar
✓ Medir y optimizar costos continuamente

Roadmap del Data Engineer 2025-2026

NIVEL JUNIOR (0-2 años)
├─ SQL avanzado
├─ Python (pandas, básicos de Spark)
├─ Un cloud provider (AWS/GCP/Azure)
├─ ETL básico con Airflow
└─ Git y línea de comandos

NIVEL MID (2-4 años)
├─ Spark / procesamiento distribuido
├─ Streaming (Kafka básico)
├─ dbt para transformaciones
├─ Data modeling (dimensional, Data Vault)
├─ Data quality (Great Expectations)
└─ Docker y Kubernetes básico

NIVEL SENIOR (4+ años)
├─ Arquitectura de datos (Lake/Warehouse/Lakehouse)
├─ Streaming avanzado (Flink)
├─ Table formats (Iceberg, Delta)
├─ Performance optimization
├─ Cost optimization
├─ ML pipelines y Feature Stores
└─ Liderazgo técnico

Tendencias 2025-2026

🔮 Hacia Dónde Va Data Engineering

  • Data Mesh: Descentralización con productos de datos
  • Lakehouse: Convergencia lake + warehouse
  • Real-time: Streaming-first architectures
  • AI/ML-ready: Pipelines diseñados para ML desde el inicio
  • Cost Engineering: FinOps para datos
  • Data Contracts: APIs formales entre equipos
  • Semantic Layer: Métricas como código
